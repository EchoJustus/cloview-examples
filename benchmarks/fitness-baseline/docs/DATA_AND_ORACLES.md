# Data, formulas, and frozen business oracles

All data in `fixtures/` is synthetic and fixed. Nothing is a user's health
record. The small fixture library has four exercises; it does not claim to be
the original application's full 25-exercise media library. No portrait or
third-party exercise image is required to run these business checks.

## Files and transport rules

| File | Purpose |
| --- | --- |
| `fixtures/demo-document.json` | English UI/effect-demo state with four exercises, one plan, three records, and two HR intervals. |
| `fixtures/demo-document.edn` | Same input data as EDN with keyword field names. |
| `fixtures/business-inputs.json` / `.edn` | 37 operation inputs without generated answers. |
| `fixtures/business-cases.json` / `.edn` | Frozen input/output cases generated by the included reference core. |
| `fixtures/muscle-dictionary.json` | Twenty stable muscle identifiers and English labels. |
| `fixtures/heart-rate-synthetic.csv` | Two explicit UTC intervals matching the first completed fixture exercise. |

JSON field names correspond to Clojure keywords, including punctuation such as
`use-hr?` and `in-month?`. Muscle-load map keys remain string muscle IDs. Error
reasons and method keywords become strings in JSON. Preserve `null` as unknown
or unavailable; do not silently change it to zero. Arrays retain order. Compare
object keys without regard to order. Compare finite floating point results with
absolute or relative tolerance of `1e-9`; IDs, counts, timestamps, dates, and
booleans require exact equality.

The generic fixture envelope is `FITNESS_BUSINESS_CASES_V1`, with `synthetic:
true` and `cases: [{id, operation, input, expected}]`. No expression strings are
evaluated. The operation dispatcher in `reference-core/runner.clj` is an exact
mapping to the included core functions, plus explicitly named projections
(filter result IDs, collision reason, unchanged-result checks).

Times are epoch milliseconds representing fixed UTC instants. Record `date`
is a caller-supplied local calendar date. Intervals are half-open `[start,end)`.
The midnight fixture already contains daily slices with a shared `group-id`:
the core does not itself discover a timezone or split a session at midnight.
A real host effect layer must supply the correct local slices, including DST.

| Cases | Required behavior |

| CAT-07 through CAT-09 | Trim/deduplicate equipment; no-equipment exclusivity; MET thresholds initialize missing intensity, while explicit intensity is independent of MET. |
| PLAN-01 / PLAN-02 | Repeated exercises have separate item identities; copied item follows its source; colliding IDs are rejected. |
| REC-01 through REC-04 | Pauses do not count; overlapping active segments merge; finishing protects record identity and is idempotent. |
| MUS-01 | Primary muscle weight 1.0, secondary 0.5, duplicates removed, primary wins. |
| HR-01 through HR-03 | Time-weighted measured HR, bounded gap hold, validation, and last valid duplicate. |
| CAL-01 through CAL-08 | MET baseline; missing weight stays unknown; incomplete/zero-duration contributes zero; optional bounded HR heuristic; planned target HR is never measured HR; overlapping logs cannot double-charge energy time. |
| AN-01 / AN-02 | Two actual sets versus one prior set; three planned items including repeated press; planned and actual are independent. |
| AN-03 through AN-05 | One midnight-spanning physical group belongs to its earliest active date; active minutes follow both daily slices. |

The Python checker independently anchors the key expected values and checks
JSON consistency and references. The Clojure runner actually executes the
copied core and compares every generated output with frozen EDN. Neither tool
proves the future framework renders controls, dispatches events, persists data,
or runs on a different Clojure host. Those require candidate-host execution.

## Compare a candidate host's actual business outputs

Run each operation against the candidate's shared business implementation and
collect its result. Use this JSON envelope (the example contains only one case
for readability; submission requires all 37 unique cases):

```json
{
  "schema_version": "FITNESS_BUSINESS_RESULTS_V1",
  "host": "jvm",
  "candidate_revision": "replace-with-tested-revision",
  "cases": [
    {"id": "CAT-01", "actual": ["press", "curl", "pushup"]}
  ]
}
```

Then run from the package root:

```text
python tools/check_fixtures.py --observed candidate-business-results.json
```

Allowed hosts are `jvm`, `dart`, and `clr`; record one file per tested host.
The checker rejects missing, extra, and duplicate case IDs; duplicate JSON object
keys; changed object keys;
array order differences; null/boolean substitutions; non-finite values; and
incorrect outputs. Integer outputs require exact integers; floating point
outputs allow absolute or relative error of `1e-9`. Booleans never count as
numbers. JSON object-key order does not matter.

A comparison pass validates the submitted data, not its origin. Accompany the
file with the real command, runtime version, tested revision, and execution log.
Copying the reference answers into an observation file is not host execution.
UI/effect acceptance remains separate from these business result files.

## Exact energy behavior used as an application oracle

This is a software regression contract, not a claim of physiological accuracy.
No medical or scientific validation is added by this package.

```text
baseline_kcal = MET * 3.5 * weight_kg / 200 * active_minutes
HR_reserve = (average_measured_bpm - resting_hr) / (max_hr - resting_hr)
HR_factor = clamp(0.75, 1.25, 1 + 0.5 * (HR_reserve - 0.6))
overall_HR_factor = 1 + HR_coverage * (HR_factor - 1)
estimated_kcal = baseline_kcal * overall_HR_factor
```

The HR factor is used only when explicitly enabled, profile values are valid,
and actual samples overlap active time. Without any matching HR, valid reps and
reference repetitions per minute can apply a frequency factor clamped to
0.75-1.25. Any matched HR disables that frequency adjustment even if HR-based
energy adjustment is disabled. A target HR never substitutes for samples.

For CAT-09, initialization thresholds are MET below 3 = low, below 6 = medium,
otherwise high; an explicitly chosen intensity remains independent of MET.
Missing or invalid calculation MET uses 3.5 and sets `estimated-met?`. Missing
positive body weight produces unknown kcal for active records. This is distinct
from zero-duration or unfinished records, which contribute zero.

The baseline paused fixture lasts 120 seconds on the clock and 90 active
seconds. At MET 4 and 70 kg its baseline is 7.35 kcal. The partial-HR fixture
has 60 active seconds, 50% HR coverage, HR factor 1.2, and 5.39 estimated kcal.
The overlapping-record daily example has only 2.5 unique active minutes and
12.25 kcal. These quantities are generated by the actual core and independently
checked by Python.

Muscle analysis is intentionally a different accounting view from daily energy:
its minutes follow valid completed record slices, while energy removes overlap
across different records to avoid double charging. Do not silently rewrite this
baseline discrepancy. If a candidate proposes a different product rule, report
it as an explicit application change, not framework parity.

## UI fixture interpretation

The default demonstration date is 2026-10-13. There are two completed press
groups on that day, 2.5 active minutes, and 2 of 3 plan items completed. The
previous day has one completed press group and 1.0 active minute. The third
planned item is an unfinished curl. The two press items deliberately share an
exercise ID but have distinct item IDs. Editing a library exercise must not
rewrite the `exercise` snapshot inside historical records.

The profile's `example?` field is true. It is explicitly a sample 70 kg profile,
not an observed user characteristic. The UI fixture's `active` is null so that
starting a training action is deterministic. No current wall-clock date is used.

The `zh` compatibility fields contain English in this package. Preserve them
only when evaluating this existing core; a future cross-host framework is free
to use a better localization model. No framework DSL, distribution mechanism,
or reader-conditional feature name is decided by these fixture files.

## Boundaries not executable in this pure-core subset

Atomic persistence, stale-snapshot rejection, asynchronous save completion,
active-session protection during sync, native file dialogs, media playback,
HTTP pairing, and Health Connect permission lifecycles belong to effect or host
integration tests. They must not be marked passed merely because these pure
business fixtures pass. No production sync secret, personal device ID, or
private data directory is included.
